# PBW 開発方針書 v1

## 1. 目的
本プロジェクトの目的は、
**局所の介入が制度を裂き、時代を動かし、やがて神話そのものを書き換えるダークファンタジー歴史生成 RPG**
を、段階的かつ破綻なく実装することである。

本書は、世界観そのものではなく、制作における
- 優先順位
- 正本
- 実装順序
- 品質基準
- 変更管理
を定める。

---

## 2. プロダクトの核
本作の核は以下の四つである。

1. **可読な不確実性**  
   プレイヤーは、危うさの輪郭が見える未知に引かれる。
2. **介入の手応え**  
   選択は必ず制度・関係・時代・神話のいずれかに傷を残す。
3. **感情の余韻**  
   成功も失敗も、苦い価値として残る。
4. **世界規模の反響**  
   ミクロ行動がマクロ・メタ・神話へ届く。

この四点のどれかが欠ける実装は、本作の核から外れる。

---

## 3. プレイヤー体験の優先順位
初期開発で優先する体験は次の順とする。

### 最優先
1. **事件や制度のほころびを読み、介入する面白さ**
2. **選択が世界の状態に返る実感**
3. **暗いが忘れにくい感情体験**

### 中期優先
4. **Era の変遷と世界史観察の面白さ**
5. **勢力外交と制度操作の面白さ**

### 後期優先
6. **神話介入・昇神・主神交代・輪廻改変の到達感**

判断に迷う場合は、上位体験を守る。

---

## 4. 正本管理

### 唯一の現在正本
- **第二部統合版 v10** を現在の制作正本とする。
- 具体的には、`PBW_SecondPart_Integrated_v10/` とその manifest / registry / sample 群を基準にする。

### 参照資料
- `StarRingCodexRPG.zip` は資料母体として保持する。
- v1〜v9 の段階ファイルは、由来確認・補助参照・ロジック追跡用であり、正本ではない。

### 優先順位
矛盾した場合は以下の順で優先する。

1. 開発方針書 v1
2. 第二部統合版 v10 manifest / registry
3. v10 sample / validation report
4. 旧版 v1〜v9
5. README やメモ

---

## 5. 最小完成形（First Playable / Vertical Slice）
初回の到達目標は、**全世界完成** ではなく、以下を満たす縦切り版とする。

### 最小完成条件
- 1 seed 世界を生成できる
- 6〜12 地域が動く
- 5〜8 勢力が動く
- 制度・条約・条項・事件ノードが発生する
- プレイヤーが 1 事件へ介入できる
- 解決結果が世界に返る
- UI で Scene / Node / World Pulse を確認できる
- その結果として Era が再判定される

### この段階で入れないもの
- 全12種族の完全固有クエスト網
- 全文化圏の祭礼完全実装
- 全神話ルートの分岐網
- マップ探索のフルボリューム
- 全ダンジョン深層の個別生成

---

## 6. 実装順序

### Phase A: Truth Engine
最初に正本となる世界更新系を固定する。

- world state
- faction AI
- diplomacy
- institution / clause
- event node
- quest generation
- quest resolution
- era update
- mythic integration

この段階では UI は最小でよい。

### Phase B: Read Model
Truth Engine から UI 用 read model を作る。

- scene output
- scene packet
- shell snapshot
- ui event envelope
- node board / world pulse / codex 用読み出し

### Phase C: Playable Loop
プレイヤー入力を read model から truth engine へ返す。

- choice -> action intent
- action intent -> resolution
- resolution -> world mutation
- world mutation -> new snapshot

### Phase D: Content Expansion
その後に、都市・神殿・文化差・会話厚み・固有イベントを足す。

## 8. UI / UX 方針

### 表示原則
- プレイヤーに最初に見せるのは **争点** であって、全因果ではない。
- 1シーン 1焦点を守る。
- 世界は巨大でよいが、場面は明瞭でなければならない。

### 段階開示
- Scene: いま危ういもの
- Node Board: 連鎖と制度破綻
- World Pulse: Era / 神話圧 / 輪廻歪み
- Codex: 背景定義と長期記録

### 隠すもの
- すべての内部スコア
- すべての生成因果
- すべての神話圧計算式

### 見せるもの
- 何が危ういか
- どの関係が揺れているか
- どの制度が破れそうか
- その介入で何が賭かるか

---

## 9. コンテンツ制作ルール

### 自動生成と手作りの境界
- **世界状態・事件・圧力・Era** は原則自動生成
- **象徴都市・象徴神殿・重要NPC・終盤神話分岐** は手作り許容

### 手作りコンテンツ追加条件
手作り要素は次を満たす場合にのみ入れる。

1. 世界法則に矛盾しない
2. 生成系から見ても異物にならない
3. 他 seed でも再利用できる抽象度がある

### 禁止
- 生成系を無視した特例ルールの乱立
- 世界法則より優先される都合イベント
- 旧資料にのみ存在する設定の再導入

---

## 10. 文体・演出ルール

### 文体層
- 地の文
- 会話文
- 神話文
- 年代記文
- UI 文

を混同しない。

### 優先原則
- Scene は読ませる
- UI は迷わせない
- 神話文は位相をずらす
- 年代記文は冷たい

### NPC 発話
既存の発話辞書に従い、
- 役割は第一声
- 関係値は扱い
- 感情値は揺れ
- 破綻は別レイヤー
で運用する。

---

## 11. バランス方針

### 基本原則
- 主人公は最初から世界を動かしすぎない
- 序盤は局所、中盤は制度、後半で神話へ触れる
- 世界は放置でも動く
- ただしプレイヤー介入でのみ「意味ある傷」が残る

### 避けるべき状態
- 毎ターン大事件で重すぎる
- 介入しても変化が見えない
- 失敗が単なる損失で終わる
- 主人公が序盤から神話を踏み抜く

---

## 12. セーブ / ロード方針

### 保存単位
- seed
- world state
- protagonist state
- institution state
- event node state
- legacies
- mythic state
- UI read model は保存しない（都度再構築）

### 原則
- **truth engine state を保存** する
- read model は派生物とする

### 互換性
- save version を持つ
- 破壊的変更時は migration table を用意する

---

## 13. 品質基準

### 実装品質
- schema validation を通る
- world -> ui 変換に null 崩れがない
- 1 seed 再生成時に致命的不整合がない
- 未介入時にも世界が回る

### 体験品質
各シーンで次の5問に答えられること。

1. 何がまだ不明か
2. プレイヤーは何を選べるか
3. 何が傷つくか
4. 何が残るか
5. どの階層まで反響するか

---

## 14. テスト方針

### 必須テスト
- seed 再現テスト
- schema validation
- null / missing key 耐性
- institution -> event node 昇格テスト
- node 解決 -> world 反映テスト
- mythic transition テスト
- ui snapshot 生成テスト

### プレイテスト項目
- 争点が読めるか
- 選択の結果が読めるか
- 一度の介入が印象に残るか
- 情報量に潰されないか
- 暗さが作業ストレスになっていないか

---

## 15. 変更管理

### 変更カテゴリ
- A: 世界法則変更
- B: データ schema 変更
- C: UI 表示変更
- D: コンテンツ追加

### 扱い
- A/B はレビュー必須
- C は体験目的の明記必須
- D は registry 追記必須

### 禁止
- 正本を更新せず README だけ変える
- schema 変更をサイレントで行う
- サンプルと正本が食い違う状態を放置する

---

## 16. 開発体制

### Codex への指示原則
- v10 を正本にする
- 旧版は参照専用
- 生成ロジックより先に UI を仮実装しない
- 変更したら manifest / registry / sample / validation を同時更新する

### 1タスクの単位
1タスクは次のどちらかに限定する。

- truth engine 側の一機能
- read model 側の一出力

複数層を一度に大改修しない。

---

## 17. 完成判定

### 第一完成
- seed 世界が生成される
- 事件が動く
- 介入できる
- UI で読める

### 第二完成
- 神話層まで一貫する
- 主神交代が起きうる
- 最終分岐が実際に開く

### 第三完成
- コンテンツ拡張後も破綻しない
- 複数 seed がそれぞれ別の歴史に見える
